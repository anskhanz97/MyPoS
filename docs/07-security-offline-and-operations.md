# Cross-cutting safety, offline and operations checklist

Every implementation ticket reads this document. These requirements are specific to a POS holding financial and employee records; they are not a substitute for module tests.

## Authentication and scope

Prefer same-origin secure sessions for browser users with CSRF protection. API tokens for devices/integrations have explicit scopes, revocation and expiry. Confirm Sanctum configuration against the chosen version. Use strong password hashing and rate limits. Cashier PINs are not global passwords: device provisioning and merchant/staff context constrain their use, attempts are limited and sensitive actions require appropriate approval.

Never trust merchant/store/register IDs alone. Test horizontal access, related-record substitution, exports, cached results, queued jobs, attachments and support actions. Platform operators do not silently impersonate owners; any support access must be explicit, time-bounded where practical and audited.

Fixed roles still need a rigorous permission matrix. Cashiers cannot see payroll, secrets, supplier balance administration or another merchant. Public loyalty is a separate minimal response surface, not an exception that exposes full models.

### Offline staff authorization snapshot contract

T008 defines the authorization payload that T023 must carry in an enrolled register's encrypted offline bootstrap. It is an authorization lease, not a portable account credential. The signed, versioned and device-bound payload contains only the membership public ID, display name, fixed role, authorized store public IDs, explicit permission codes, issue/expiry timestamps, configuration version and a revocation watermark. It excludes email addresses unless the register workflow needs them, all payroll and salary values, platform-operator status, password data, raw PINs, reusable server PIN hashes, integration secrets and broad merchant records.

Any offline PIN verifier must be derived separately for the enrolled device, encrypted at rest with device-held material and usable only inside that device, merchant and store scope. It must never appear in API responses, logs, exports, telemetry or audit metadata. First provisioning and lease renewal require connectivity. T023 must choose and test the bounded lease duration, encrypted IndexedDB storage, tamper detection, clock-skew handling and schema migration behaviour; a client must deny offline staff switching once the lease expires or its signature/version cannot be validated.

The register records which authorization snapshot and staff identity accepted each offline command. Reconnection reconciles the server's current membership status, store assignments, PIN-change timestamp and revocation watermark before accepting new offline work. Deactivation, role/store changes, PIN changes and device revocation prevent future authorization as soon as the register reconnects; already accepted local cash sales remain preserved for controlled reconciliation. A local denial does not delete a cart or its durable pending commands.

Online approvals use short-lived opaque tokens that are permission, action scope and target bound, expire after five minutes and are consumed once. T023 may support an offline exceptional action only when an unexpired cached policy expressly permits it and a different locally authorized manager or owner enters a PIN on the same enrolled register. The client must record the approver, reason, target and snapshot version for later server reconciliation. Otherwise the action remains unavailable until online. An offline approval never becomes a general manager session and never authorizes payroll, integrations, device administration or merchant settings.

## Financial and data protection

No card numbers/CVV or bank credentials are stored by manual external-payment recording. Store only necessary provider/reference metadata and confirmation provenance. Mask logs and diagnostics; do not serialize full requests containing private fields. Separate public, merchant and support DTOs.

Merchant integration credentials are encrypted with the application key and never returned after write; responses expose only credential-presence and safe status metadata. Secret updates use explicit fields so ordinary settings edits cannot erase or disclose them. Meta/Twilio callbacks use provider-specific verification/signature checks over the original request material, are rate limited and deduplicate provider event IDs before changing state. Callback errors and connection tests must redact tokens, signatures, phone numbers and response bodies. Provider configuration never grants authority over sales, tenders or files outside the adapter's named capability.

Posted transactions have reversal/correction workflows. Audit who, when, scope, reason and relevant before/after values without duplicating secrets. Rebuildable projections do not replace source ledgers. Imports are bounded, validated and staged; exports prevent spreadsheet formula injection and unauthorized broad data access.

## Offline scenarios to test

- Server reachable versus browser connectivity flag; use real request outcomes.
- Initial provisioning requires online access; subsequent valid register restart can work offline.
- Power interruption after local commit, after server commit and before acknowledgement.
- Retry of same UUID/body; same UUID with changed body; reconnect from two tabs.
- Expired pricing/staff lease, revoked user, subscription change and pending local sales.
- Cache/schema upgrade with unsent commands, quota exhaustion, denied persistence and private-browsing restrictions.
- Device clock drift, negative stock, expired batch and promotion schedule across midnight.

T015 batch-selection snapshots carry the server-derived store business date, exact batch IDs, quantities, expiry-date copies, a content hash and a short expiry. They are evidence for later checkout/offline reconciliation, not reservations or sale authority. T022/T023 must re-resolve every batch, compare the stored expiry fact, use server store time and lock current batch balances before posting. A stale, missing, changed or now-expired batch returns an actionable conflict; the client must not silently substitute another batch or use its own clock to override the server.

T021 online cart mutation uses an optimistic version inside a row-locking transaction. Tenant, store and register ownership is checked at both route/service boundaries and through composite database keys. Product IDs, customer IDs, units, extras and batch snapshots are resolved again within server scope. Scanner input is restricted to the configured barcode character set and never supplies a trusted price. Browser scanner focus uses the `/` shortcut only when the user is not editing another input, textarea or select. Network interruption keeps the cart visible with an explicit retry state; it does not show an unconfirmed quote or payment success.

T016 transfers are online management operations. Creation requires inventory-management permission in both source and destination stores; dispatch is source-scoped and receipt rechecks destination authorization. Lists expose only transfers connected to the requested authorized store, and stocktake reads remain store-scoped. Transfer mappings, short/excess reasons, cancellation and stocktake posting are audited. Neither cached register state nor an offline manager snapshot authorizes dispatch, receipt, mapping changes or stocktake posting.

T017 supplier and purchase-order endpoints require `purchasing.manage` and an assigned store context. Supplier records remain merchant-scoped, while every purchase order, read, mutation and PDF is restricted to its owning store. Supplier contact values and generated documents are private merchant data and use no-store responses; PDF rendering permits no remote fetches or embedded PHP. Issuing, amending, cancelling and archiving create audit/history evidence. Purchase-order creation, issue, edit, cancel and export are unavailable offline.

T018 receiving and reversal require `purchasing.manage`, the PO/receipt's exact merchant and store, and an active inventory location in that store. Valuation reads require `inventory.view`. Receipt payloads never accept arbitrary merchant, supplier, variant or conversion ownership fields; those come from the locked order line. Receipt posting and reversal are online-only, audited commands with stored fingerprints. Supplier charges contain operational amount/reference evidence, no bank credentials or payment claim. Outbox payloads contain IDs and versions rather than supplier contact data. Concurrent writers lock PO and store/variant cost rows in deterministic command order; no offline cache can authorize receiving or retroactive valuation changes.

T019 return, credit confirmation, payment and reversal commands require `purchasing.manage` in the exact store and run online in one database transaction with stored command fingerprints where retries are possible. Route payloads select only source receipt/charge public IDs; merchant, store, supplier, batch and variant ownership are derived and rechecked server-side. A manager sees a store statement; merchant-wide aggregation requires `report.consolidated` and therefore an owner under the fixed launch roles. Payment references and methods are evidence only: MyPoS stores no supplier bank credentials and initiates no funds transfer. Outbox events expose identifiers and status, not contact or bank data.

T020 cash-session operation requires `cash.operate` in the exact assigned store. Cashiers may open a register session, post paid-in evidence, hand over their current custody and submit a blind count. Paid-out and supplier cash-payment movements require `cash.manage`; no-sale opening requires `drawer.no_sale`; approving or reopening a variance requires `cash.variance.approve`. Route scope derives the merchant, store, register and session relationship server-side. Counts, handovers, movements and reviews are immutable, while session projections use optimistic versions and row locks. Outbox payloads contain identifiers, movement kind and source identifiers only. They exclude staff credentials, supplier contact details and free-form reasons.

T020 records pending offline counts but does not claim a completed offline close. `close_pending_sync` remains an active session, expected cash is concealed, and the UI says unresolved. T023 must replace client-supplied pending evidence with the verified device command queue/reconciliation status and exercise crash, two-tab and late-arrival behavior. T022 owns idempotent sale/refund movement consumers. No physical cash drawer hardware command is claimed by T020.

T022 accepts only scoped active quotes and open register sessions. A cash sale requires the authenticated actor to be the current drawer custodian. Manual card, wallet and bank tenders require a nonempty external reference plus `confirmation_source=staff_declaration`; the API does not accept or retain PAN, CVV, PIN or track data. The UI labels this provenance and separately reports sale finality, receipt readiness, print state and fiscal state. Lost responses are recovered by the merchant/store/register-bound client transaction lookup or by replaying the identical command, never by inventing a fresh payment. Deterministic register-first locking and database uniqueness serialize concurrent duplicates; transaction retries remain bounded for deadlocks.

T024 keeps the Ed25519 signing seed server-side and gives the browser only short-lived signed authorizations. Print and drawer helper callbacks require the enrolled device credential and exact merchant/store/register ownership. Helper event IDs and attempt numbers are replay checked. One original job is enforced in the database; every reprint has a reason and visible copy mark. The allowlisted loopback TLS helper protocol accepts only receipt commands and register-scoped drawer commands, never arbitrary paths, URLs or shell operations. Offline authorization is bounded by the cached device lease and fence. Physical helper, printer, driver and drawer combinations remain unqualified until the hardware matrix is run.

T025 display pairing codes are stored only as keyed hashes, expire after ten minutes and are consumed once. Display tokens are random, stored only as SHA-256 hashes and never grant staff/device permissions. Reads require the exact active, unexpired pairing and token; staff publishing/revocation requires `sale.create` in the exact store/register scope. The server emits product display names, quantities, extras, discounts and totals only. It excludes customer contact/loyalty data, staff identity, approvals, internal cost/margin and external-payment references. Same-device channel IDs travel in the URL fragment so normal HTTP logs do not receive them; projections reject another register and advance monotonically. No customer-display route finalizes, edits, returns or refunds a sale.

T026 return and exchange commands require `return.create` in the exact merchant/store context and validate the original sale, current register session, lines, tenders and public IDs again inside the transaction. The server ignores current catalog prices and accepts no client-computed refund total. Late approvals are short-lived, one-use and command-UUID-bound. Refund evidence stores a reference and confirmation source, never card credentials or an assertion that MyPoS contacted a provider. A pending external action remains visible and cannot complete an exchange. Return outbox events contain document identifiers, total and state; downstream loyalty and fiscal consumers must independently authorize and deduplicate their later T027/T035 effects.

T027 programme publication, reward configuration and member creation require `loyalty.manage`; cashier lookup and cart redemption use the existing `sale.create` boundary. Every lookup filters by the authenticated merchant, and the merchant-wide member response does not reveal another store's operational customer record. Reservation routes revalidate merchant, store, register, cart, customer link, reward and balance inside the transaction. The server derives points and reward discount from published records. Idempotency keys cannot be reused with another payload. Redemption is unavailable in offline snapshots and commands. The scheduler posts expiry through the same locked ledger and `withoutOverlapping`; retry is safe because each earn can produce only one expiry entry. Ledger changes emit outbox events without phone numbers, customer profiles or payment evidence.

T028 is deliberately public and does not claim phone ownership or privacy. Programme metadata is limited to the active slug, name, reward labels/thresholds and notice. Join is capped at five attempts per minute per slug/IP, lookup at ten, and programme reads at sixty. Unknown members return no member DTO. Success/not-found telemetry stores only HMAC phone and IP values plus a bounded user-agent prefix; raw phone and IP are not copied into the abuse table. Responses never expose the canonical phone, full name, operational customer links, email, address, receipt/history, ledger entries, store profiles, discount amount, QR/token or any redemption authority. Only authenticated staff checkout can reserve or spend points.
- Browser clear-data and device-loss limitations; provide recovery procedures without promising impossible recovery.
- Offline print helper unavailable, duplicate print request, drawer command and explicit reprint.

Never discard an accepted local cash sale just because later server validation fails. Route conflicting records to a controlled reconciliation state with preserved evidence and cashier-visible status. Do not falsely label quarantined submissions as fully posted. T023/T035 define fiscal treatment if an outage affects legal issuance.

## Operational readiness

Use structured correlation identifiers and metrics for checkout latency/error rate, pending offline age/count, rejected submissions, queue lag, print failures, email failures, fiscal exceptions and balance discrepancies. Set actionable alert thresholds using actual pilot/load measurements.

Backup MySQL and required object data with encryption/access controls. Verify restoration, migration rollback/forward strategy, worker/scheduler operation and tenant-level recovery procedures. Record RPO/RTO targets separately from achieved restoration times. Exporting one merchant is not automatically a consistent restore procedure.

Deployment requires health checks, HTTPS, secret management, database least privilege, bounded connection pools, queue retry limits and log retention. Avoid long migrations that lock checkout tables during trading. Keep API compatibility with supported pending offline clients.

Document merchant onboarding, opening balances, first sale, device setup, staff training, subscription renewal and offboarding/export. Billing enforcement must allow submission/recovery of valid pending offline records even if new selling is restricted by entitlement policy.

### Subscription restriction and offboarding hooks

Subscription lifecycle records are separate from POS tenders and merchant financial ledgers. `trial`, `active` and `grace` permit new operations; `restricted` and `cancelled` deny them. Every state continues to permit authenticated export, support and submission/recovery of already accepted offline work. A manual subscription payment records external evidence and the platform operator who checked it; it does not claim that MyPoS acquired or independently verified money.

Cancellation never deletes merchant data. The `closed` merchant transition is deliberately unavailable until T033 provides a verified portable export and T036 defines retention, legal hold, backup and erasure procedures. That future command must reject closure while offline or fiscal records remain unresolved, record the export/retention decision, revoke new device leases and preserve the minimum immutable financial/audit records required by the approved policy. Support access requires a merchant-scoped, purpose-bound, expiring grant; each diagnostics read creates a separate platform audit record.

### Register provisioning and configuration contract

T010 provisions a register through a ten-minute, one-time pairing code issued by an authorized owner. The code is stored only as a SHA-256 lookup hash and is invalidated after consumption, replacement or reissue. Successful consumption returns a 64-character device key once; only its adaptive hash is stored. Public pairing and bootstrap attempts are rate limited. Initial pairing requires connectivity, and an active enrollment has a 72-hour online lease pending the offline policy and renewal implementation in T023.

Each device belongs to exactly one merchant, store and register. Bootstrap accepts the device public ID plus the device key and returns only that tenant, store, register, effective configuration, lease metadata and coordination identifiers. It excludes credential hashes, pairing hashes, user records and unrelated merchant data. Revocation increments the credential version, records the actor/reason, revokes active staff sessions and immediately denies bootstrap. Controlled replacement also revokes the displaced device and its sessions, increments the register fencing epoch and preserves lifecycle history.

The bootstrap coordination contract gives each device a stable writer-lock name and current fencing epoch. T023 must implement the browser-side lease/election, attach the device/config version and fencing value to offline commands, reject stale writers server-side and test crash/reload/two-tab races. The current T010 interface labels this as a coordination hook; it does not claim that browser arbitration is already active.

T023 implements the coordination hook with a Web Lock per enrolled register and a `BroadcastChannel` ownership signal. The server independently checks the current device fencing epoch and signed snapshot evidence, so browser arbitration is an operational safety layer rather than an authorization boundary. Device bootstrap and reconciliation use a rate-limited `X-Device-Key`; only its adaptive server hash is stored. Recovery submission permits the still-valid secret for a replaced/revoked/expired enrollment so already committed evidence can be classified, while new snapshot issuance remains denied.

Offline storage requests persistent browser storage and reports denial as best-effort. The application caps policy at 10,000 pending sales or 100 MiB within a 250 MiB managed budget and keeps a 20% free target. Quota failure cannot display sale completion. Logout, service-worker update and theme change do not clear unresolved records. Diagnostic export contains bounded sale/command evidence and excludes device keys, reusable PIN material and integration credentials. Physical loss or browser-site-data clearing cannot be presented as recoverable local evidence.

Primary browser guarantees were checked against the [IndexedDB 3.0 transaction model](https://www.w3.org/TR/IndexedDB-3/), [Web Locks API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API), [persistent storage](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria) and [Service Worker API](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API) on 2026-09-29. These sources support the chosen mechanisms; the test suite remains the evidence for this application’s behavior.

Settings are append-only versions with a publication time, effective time and optimistic expected version. Resolution merges the current merchant version with the current store override; future versions remain retained but do not apply early. Promotion mode is available only at merchant/store scope, never register scope. Hardware configuration represents declared or unconfigured state and does not claim physical connectivity. Settings and lifecycle audit metadata contain identifiers and changed field names, never pairing codes, device keys or credential hashes.

## Test strategy

Use focused domain tests for arithmetic/state transitions, MySQL integration tests for transactions/locking, API authorization tests and browser end-to-end tests for core journeys. SQLite alone cannot prove MySQL locking/constraint behaviour. Browser offline and hardware tests require their actual environment or an explicitly labelled simulator plus later device qualification.

Do not write tests merely asserting a constant equals its implementation. Prefer business invariants, concurrency, retries, permissions and realistic failure scenarios. Run ticket-relevant checks first; broaden only when changed dependencies justify it. Never run source projects' tests against their existing environment without verifying database isolation.
