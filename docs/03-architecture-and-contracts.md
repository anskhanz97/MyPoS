# Architecture, contracts and engineering defaults

Version 1.0 — 2026-09-28. These are proposed engineering defaults, not fabricated research results. Tickets T002–T004 validate and freeze them before application implementation.

## Application shape

Use a Laravel modular monolith and Vue 3 with TypeScript. Prefer one repository with a same-origin deployment, domain-organized backend services and versioned JSON endpoints under `/api/v1`. Do not create microservices for each module. Separate the application server, worker process and scheduler operationally without splitting domain ownership.

Use MySQL/InnoDB for authoritative writes. Evaluate Redis for production queues, cache, rate limits and coordination; never make a cache the only record of a paid sale. Use an object-storage abstraction for exports and attachments. Framework/runtime versions are selected from current official support documentation in T002 and pinned in lockfiles in T005.

Suggested module names: Platform, Identity, Merchants, Catalog, Pricing, Customers, Inventory, Purchasing, Checkout, Payments, Returns, Loyalty, Workforce, Payroll, Cash, Expenses, Reporting, Notifications, Integrations, Fiscal, Devices and ImportsExports. Domain services execute business commands; controllers validate and authorize; read resources serialize minimal responses. Avoid a generic unrestricted table editor.

Integrations are merchant-owned adapters behind one provider catalogue. Non-secret settings and encrypted credential payloads live in versioned merchant records, so owners configure them in the application without deployment changes. Controllers never return credentials. Staff consume a redacted active-capability view; jobs resolve the encrypted configuration only when executing authorized work. Provider callbacks authenticate before tenant-scoped lookup, deduplicate external event identity and update delivery evidence monotonically. No connector may post or mutate a core business aggregate outside its domain command boundary.

## Tenancy and identity

Separate platform administrator identities from merchant owner/manager/cashier roles. Every merchant-owned record has an explicit tenant boundary. Store and register membership must be derived from authorized server context, not trusted client IDs.

Fixed role baseline: owner controls merchant settings, subscriptions view, salaries/payroll approval and high-impact corrections; manager operates stock/purchasing and approved day-to-day workflows and can approve exceptional returns; cashier sells and performs narrowly permitted cash tasks. T008 freezes the detailed matrix; manager access to payroll amounts is denied by default. Attendance identity does not imply a login account.

Shared/independent operational catalogs use a documented scope key and referential constraints. Do not represent independent-store customers as globally interchangeable. Merchant-wide loyalty membership links separately to permitted operational customer records. The same phone can occur in different merchants without linking them. All lookup deduplication is within an explicit merchant/program boundary.

The catalog uses a merchant scope key for shared catalogs and a store scope key for independent catalogs. SKU and barcode uniqueness includes that scope, so independent stores may intentionally reuse identifiers. Shared products have explicit per-store availability rows; a newly added store starts without an availability row until an administrative catalog decision makes the product available. Product, variant and image reads re-check merchant, effective catalog scope and assigned-store permission at the server boundary.

Each product has exactly one default variant. Units convert only from a named sale/purchase unit to the variant's base unit using positive decimal factors, avoiding arbitrary conversion graphs. Fixed bundles reference finished-product variants and are checked for direct and nested cycles before their structure version advances. Extras may change price and optionally consume a configured finished-product variant quantity; they never model ingredients or preparation. Structural versions protect concurrent bundle and batch-tracking changes, while archive timestamps retain historical references.

Barcodes remain strings so leading zeros survive. Exact assigned barcodes resolve before scale-label formats. Scale formats are merchant defaults or store overrides with bounded, non-overlapping product/value slices, explicit quantity-versus-price meaning, decimal places and optional EAN-13 check-digit validation. The application does not assume a national label layout or claim direct scale connectivity. Catalog resources return public UUIDs and decimal strings; private storage paths and internal numeric keys never leave the API. Product images use validated image types/dimensions, tenant/product paths and authenticated streaming.

Operational customers follow the merchant's immutable shared/independent mode: shared profiles use a null store scope, while independent profiles belong to exactly one store. Exact phone/email duplicate review never crosses that scope. Pakistan numbers are normalized to E.164 `+92` form while the entered display value is retained. A phone is a search attribute, not a global identity key: the same number may identify separate operational profiles in different merchants or independent stores. Customer groups use the same scope as their profiles. A separate, explicit link may connect multiple scoped profiles to one merchant-wide loyalty member only after normalized phones match; it never grants access to another store's full profile.

Cashier customer reads use a reduced serializer and cashier writes accept only checkout contact fields. Receipt-email preference and marketing consent are separate values; marketing opt-in records its source and time. Customer choice remains optional during checkout. When chosen, the checkout obtains an immutable minimal customer snapshot, and later profile edits or archive operations cannot rewrite a posted sale. Archive removes a profile from default search and new sale association while preserving its record and links for authorized history.

Proposed IDs: internal immutable database keys plus opaque public IDs; client-generated transaction UUIDs for offline commands. Idempotency uniqueness includes tenant, command type and caller/device scope. Client idempotency keys never grant access.

## Business commands and state

Write operation-oriented services for sale finalization, purchase receiving, inventory transfer receipt, return approval, cash closeout, payroll posting and loyalty redemption. A generic `POST invoices` endpoint is not sufficient for atomic checkout.

Candidate endpoint families (final payloads frozen in T004 and extended by their owning ticket):

- `/merchants/{merchant}/stores/{store}/registers/{register}/carts`, cart detail/scan/suspend/resume/quote commands, `/sales`, `/sales/{id}`, `/sales/{id}/returns`, `/exchanges`.
- `/merchants/{merchant}/stores/{store}/registers/{register}/cash-sessions`, then scoped session detail, movement, handover, close-count and review commands.
- `/purchase-orders`, `/purchase-orders/{id}/receipts`, `/purchase-returns`, `/supplier-payments`.
- `/stock-transfers`, `/stocktakes`, `/inventory-adjustments`.
- `/loyalty/members`, `/loyalty/redemptions`, `/public/loyalty/{slug}/join`, `/public/loyalty/{slug}/lookup`.
- `/customers`, `/customers/duplicates`, `/customers/{id}/sale-association`, `/customers/{id}/loyalty-link`, `/customer-groups`.
- `/offline/bootstrap`, `/offline/transactions`, `/devices`, `/print-jobs`.

The public join and public lookup have distinct server commands even when the UI presents one form. Never refresh a member page by replaying enrollment.

T028 implements that split as `GET /public/loyalty/{slug}`, idempotent `POST .../join` and read-only `POST .../lookup`. The slug resolves exactly one active programme before a phone is normalized. Join briefly locks the programme row, which serializes duplicate enrollment for the same programme without relying on browser timing; the merchant/phone unique key remains the database backstop. An enrollment record stores the command hash, optional valid merchant-store attribution and marketing consent separately from membership eligibility. Lookup reads the member and balance but creates no member, enrollment, welcome credit or ledger entry. Both commands map through a purpose-built public DTO with masked name/phone, four-decimal balance and only currently affordable active reward labels and point thresholds.

Use explicit state machines. At minimum distinguish draft, posted/finalized, reversed/corrected and rejected where relevant. Do not soft-delete posted financial effects or mutate their historical totals. Cancelling a draft and reversing a completed transaction are different operations.

## Monetary arithmetic and quantities

Currency defaults to PKR at launch. Do not imply multi-currency checkout. Represent API money/quantity values as decimal strings, not binary floating-point amounts. Proposed storage: sufficiently sized `DECIMAL` columns, with more internal precision for rates, unit costs and fractional quantities than receipt totals. T004 freezes scales, limits, rounding stage and maximum amounts with examples.

Sale snapshots preserve description, SKU/barcode used, quantity/UOM conversion, unit price, promotion allocations, tax basis/rates, final totals and sale-time cost. Tax/price changes cannot rewrite old sales. Refund calculations use original line allocations and remaining refundable quantity/value. Split rounding must conserve the original total exactly.

Pricing publishes immutable merchant-default or store-override snapshots with effective windows, a content hash and an optimistic version. An effective signature such as `m7-s2` identifies both layers used for a quote. Store prices override matching merchant variant/customer-group entries while absent store entries inherit the merchant value. Independent catalogs publish store-scoped snapshots only. Mode comes from the effective store override when one exists, otherwise the merchant default.

T021 implements checkout as a mutable register-bound cart aggregate. Every mutation locks the cart row, requires `expected_version` and increments the version; stale writers receive a conflict rather than a last-write-wins overwrite. A full-set replacement resolves variant, unit conversion, extras, optional customer and batch-selection evidence from server records. Scanner commands resolve exact/configured scale barcodes; only the same configuration hash (variant, unit, extras, batch and normalized discount) is incremented. Suspended carts remain editable only after an explicit resume and do not reserve inventory. Quotes are append-only snapshots of the current cart/pricing versions with a five-minute validity marker; they calculate no sale, tender, coupon consumption or stock movement.

T022 consumes one exact, unexpired cart quote in a register-scoped sale command. It locks the register before resolving either command identity, then locks the quote, cart and cash session in a deterministic path. The command requires `sum(tenders) - cash_change = quoted gross`, and change cannot exceed cash received. Cash contributes its net amount to the drawer; staff-declared external card, wallet and bank records contribute no cash and never imply provider verification. Sale, line/extra/tender snapshots, stock and valuation effects, limited coupon claims, net cash movement, immutable receipt snapshot, converted cart, audit and outbox records commit in one MySQL transaction. A repeated identical idempotency key and client transaction ID returns that sale; any changed identity or body conflicts.

T026 posts only original-sale-linked returns. It locks the register, original sale, active cash session and selected sale lines before calculating cumulative proportional entitlement from the frozen original `pre_discount`, discount, net, tax and gross values. Each component rounds cumulative entitlement to two decimals; the new document receives the difference from prior returns, so the final partial return absorbs residual rounding without exceeding original quantity or value. A restock maps each new stock movement to its exact original sale movement in `sale_return_stock_effects`, restores the proportional six-decimal quantity at the original recorded unit cost and rejects an expired batch. Damaged, expired and discarded dispositions create no stock effect.

T027 implements loyalty inside the modular monolith rather than through a till/cloud bridge. One merchant owns one programme and a sequence of immutable earning versions. Rewards are versioned operational records, while every earn, redeem, expiry and refund reversal is a signed four-decimal ledger entry with a unique merchant/source/kind identity. A locked balance row is a rebuildable projection of that ledger. Redemption first creates a five-minute, idempotent reservation against the available balance, binds it to one online cart and invalidates the old cart quote. Pricing allocates the configured reward discount across remaining line value before tax and freezes the reservation identity in the quote. Sale finalization locks and commits the reservation, appends the redemption debit and FIFO earn-consumption evidence, then appends the new sale earn in the same database transaction. Offline commands cannot carry a reservation; an accepted offline sale uses the same finalization service and earns only after authoritative server acceptance.

The return service calls the loyalty ledger inside its existing transaction. Cumulative points reversal is `floor(original earned points × cumulative returned net ÷ original sale net, 4)` less prior reversal entries. The resulting debit is source-linked to the return and may make the balance negative when the original points were already spent. This is a points repayment state: later earns raise the balance toward zero and no money debt, tender or customer credit is created. The hourly expiry command locks an earn, subtracts its recorded FIFO consumptions and prior expiry, caps the debit at the current positive balance, and uses the earn public ID as its replay identity.

The ordinary return window defaults to seven days and accepts a merchant/store setting from 1–30 days. A late command consumes a manager/owner approval bound to permission `return.create`, target type `sale_return` and that command's idempotency UUID; an identical replay returns before trying to consume the approval again. Cash refunds post a source-linked negative movement in the currently open register session. External refunds are either backed by an actual staff-declared reference or remain `refund_pending` until the separate confirmation command records evidence. An exchange wraps the return and fully settled replacement `FinalizeSale` call in one outer transaction, links both documents and records the absolute difference plus `customer_pays`, `customer_refund` or `even` direction.

Manual mode skips automatic rules. Advanced mode evaluates scheduled prices and line promotions, then multi-buy/mix-and-match, coupons and authorized manual discounts before tax. Rules have priority, stacking and an optional exclusivity group. Same-priority exclusive candidates choose the greatest valid discount, then immutable public rule ID. Largest-remainder allocation uses line sequence and line ID as its stable tie break. Quote calculation never consumes a coupon; T022 must lock and claim globally/per-customer limited coupon usage idempotently during finalization. Online quote time is server-controlled, and a stale pricing signature returns a conflict requiring explicit reprice.

Moving weighted average is the selected valuation method. Batch selection is separate from valuation. T018 defines costs for zero/negative stock, backdated receipts, stock transfers and subsequent reconciliation. Do not silently report unknown margins as zero or promise final profitability while cost corrections are pending.

## Transactions, side effects and concurrency

Within the authoritative database transaction, validate scope/state, acquire necessary deterministic row locks, commit core records and append durable outbox work. Dispatch email, reporting refreshes and fiscal work after commit. Workers use deduplication and retry classification. Exactly-once network delivery is not promised; effectively-once business effects are required through idempotency and uniqueness.

Store an idempotency request fingerprint and original result. Repeated identical commands return the original outcome; the same key with a different body is rejected. Resolve uncertain commit results by querying identity rather than issuing a fresh sale.

Inventory and loyalty use append-only ledgers with reversible entries. Balance projections are rebuildable and periodically reconciled. No observer should trigger uncontrolled duplicate financial effects on every model update.

The T014 inventory implementation makes the movement ledger authoritative and treats `stock_balances` as a rebuildable projection. Every posting carries a stable source type/reference/line/effect identity and a payload fingerprint. An exact retry returns the original movement; reuse with a changed payload conflicts. Writers lock the balance dimension before inspecting the source identity so concurrent first writes and retries acquire rows in one deterministic order. A correction appends an equal-and-opposite movement linked to the original; movement update and delete operations are rejected by the model boundary.

Locations belong to one merchant/store and declare `sellable`, `unavailable` or `quarantine` disposition. Product scope is re-resolved from the merchant's locked shared/independent catalog mode for every command. Quantities are converted to the variant base unit before hashing and posting. Fixed bundles expand recursively to stable leaf finished-product effects, so the same source retry cannot duplicate a component movement. Negative balances remain visible and auditable. They are not silently clamped, and they do not grant permission to use unavailable or expired stock.

Reconciliation first reports each ledger/projection mismatch without changing it. A manager must submit an explicit confirmed rebuild and reason before the projection is repaired from ledger sums. Unit-cost and cost-state columns are compatibility placeholders owned by T018; T014 does not infer valuation. T015 may add a batch dimension to the same movement model without introducing a second quantity ledger.

T015 adds an optional batch identity to that same movement ledger and maintains a second rebuildable projection by store, location, variant and batch. A tracked product requires a valid batch on every ordinary movement. Enabling tracking on stock already on hand is a dedicated idempotent conversion: it rejects negative balances, covers every non-zero balance exactly, appends one unallocated release and identified batch additions whose aggregate effect is zero, then advances the product structure version. Shared products require coverage and authorization across every store that holds stock.

The expiration boundary is a store-local business date. Stock is sellable through the printed expiry date and becomes expired at the start of the following local date. FEFO proposes positive quantities from non-expired batches by expiry date, then code and immutable ID. Manual selection may choose another non-expired batch but must cover the requested quantity exactly. A selection snapshot lasts 15 minutes, records batch IDs, quantities, expiry facts, business date and a content hash, and reserves no stock. Finalization must revalidate and lock the chosen batch balances; a missing, changed or newly expired fact causes a visible conflict. Batch choice remains physical traceability and does not select the T018 moving-average valuation layer.

T016 models a transfer as separate dispatch and receipt commands. Dispatch locks and removes source stock once, freezes the mapped destination quantity and creates the in-transit fact; one or more receipts add destination stock once. Partial receipt leaves a visible remainder. Closing short or accepting excess requires an explicit resolution and reason, and the recorded shortage/excess remains on the line. Shared catalogs preserve the variant directly. Independent catalogs require a previously audited directional variant mapping with a frozen positive source-to-destination base-unit factor; names, SKUs and barcodes never imply a mapping. Batch code, expiry and receipt provenance survive the route, while T018 remains responsible for valuation.

A stocktake captures a baseline movement ID and balance for every location/variant/batch dimension. Each physical count records a later movement cutoff, then derives its expected-at-count quantity from the baseline plus authoritative movements through that cutoff. Posting appends only the resulting discrepancy as a `stocktake` movement. Movements after the cutoff remain untouched, so a live sale during or after counting is never erased by replacing the current balance with a stale physical number. Counting, review and posting use optimistic versions; posting also has a stored idempotency fingerprint.

T017 keeps supplier planning separate from inventory and liabilities. Suppliers are merchant-owned and may be referenced by every authorized store. Purchase orders are store-owned, use `draft`, `issued`, `partially_received`, `received` and `cancelled` states, and preserve product, SKU, purchase-unit factor, expected unit cost and tax-reference snapshots on each line. Issuing is an idempotent planning command and posts no stock, cost or supplier balance. Amendments increment an optimistic version and append a full history snapshot; once any quantity is received, a line cannot be removed or reduced below that fulfilled base quantity. Cancellation records only the remaining ordered quantity as cancelled and leaves received/returned facts intact for T018/T019.

The purchase-order PDF is rendered server-side from the same authorized historical model. It is an A4, light-background planning document in PKR and explicitly states that stock and supplier balances change only through later receiving. The renderer disables remote resources and embedded PHP. T034 may attach this generated artifact to an email command later; T017 performs no external send.

T018 posts a goods receipt as one store-scoped transaction: it locks the purchase order and each product valuation dimension, validates the optimistic order version and remaining quantities, records the immutable receipt/cost snapshots, posts stock, advances PO progress, creates a supplier charge entry and writes an outbox event. Receipt idempotency covers the full canonical payload. Recoverable tax is supplier-charge evidence but is excluded from inventory cost; merchandise plus explicitly capitalized landed cost forms inventory value. Batch-tracked goods require code and expiry, and an already-expired batch can enter only quarantine or unavailable stock.

Moving average is projected per store and variant, independently of physical location and batch picking. Positive stock uses the frozen six-decimal weighted-average equation. An issue uses the average known at posting; crossing below zero makes the cost state provisional. A later receipt resolves the negative quantity at actual receipt cost and records the variance separately, while any residual positive stock starts at that receipt cost. Unknown historic stock keeps value and margin visibly pending. Backdated documents retain their effective timestamp but apply at the current immutable valuation sequence. A receipt reversal restores its recorded prior valuation snapshot only when every affected receipt entry is still the latest entry and its stock remains in the original location/batch; otherwise the API requires a later documented adjustment rather than rewriting intervening history.

Transfer dispatch freezes the source moving-average cost. For independent catalogs, destination cost per base unit is source cost divided by the frozen source-to-destination quantity factor, conserving total value. Destination receipt applies that frozen cost to its own moving average; a transfer is never a supplier purchase or supplier charge. Pre-T018 stock with no known cost continues as `pending` instead of being silently valued at zero.

T019 separates three procurement facts. A purchase return is a physical, store-scoped movement linked to exact receipt lines, location and batch; it issues inventory at the current moving-average snapshot. Its supplier-credit entitlement comes from the original receipt charge, using cumulative proportional entitlement so repeated partial returns reconcile to the original two-decimal total. The credit begins `expected` unless a supplier credit-note reference is already present, and only `confirmed` credits reduce the operational supplier balance. A tail-safe return reversal appends stock, cost and credit reversals and restores the prior valuation snapshot.

A supplier payment is an immutable record of an external settlement, never an instruction to a bank. Explicit allocations may not exceed either the payment or a charge's current open amount; the remainder stays visibly unallocated. Reversal appends a negative payment and matching negative allocations. Store statements are available to authorized purchasing staff, while a merchant-wide statement requires the consolidated-report permission. The balance projection is `charges - confirmed credits - recorded payments`; expected credits remain visible outside the balance until confirmed.

## Offline boundary

Vue PWA caches the application shell, explicitly versioned catalog/pricing/tax snapshots and minimal permitted staff/device context. Store pending sales in IndexedDB with atomic local writes. Online server quote remains authoritative for normal sales; offline calculation must use the same specified arithmetic and versioned rules, tested against server fixtures.

Allow cash and cached pricing/promotions plus permitted manual discounts. Block loyalty redemption, external payment confirmation, remote stock transfers and new purchasing/payroll writes offline. Loyalty earning occurs after server acceptance. Make unsupported actions visibly unavailable.

First provisioning requires connectivity. A previously provisioned register should restart offline within its defined authorization and snapshot validity. T023 specifies supported outage age and storage bounds from evidence. Never silently clear unsent sales on logout, tenant switch, reinstall, quota pressure or update. Use a visible unresolved-sales queue and controlled recovery/export with tenant protection.

Multi-tab register ownership needs leases/coordination. Two browsers must not both assume exclusive drawer/device control. No local-network shared-store server or shared offline cart synchronization is in launch scope.

T010 assigns every provisioned device a credential version, register fencing epoch, bounded lease and composite effective-settings version. Device bootstrap returns a stable writer-lock name for browser coordination. T023 owns the actual `BroadcastChannel`/Web Locks election and server-side stale-fence rejection; all later register commands must carry the device identity, protocol version, configuration version and fence used to create them. Register replacement advances the fence so an older browser cannot silently resume exclusive device work.

Settings use append-only merchant defaults and store overrides with optimistic version checks and effective times. The resolver applies only published versions whose effective time has arrived, then recursively overlays store values on merchant values. There is no register settings endpoint. Device capabilities and hardware settings describe intended support and configuration; printer, drawer and customer-display connectivity remain explicitly unconfigured until their owning tickets verify an actual transport.

## Interfaces and events

T004 creates OpenAPI schemas, common validation/error envelopes, pagination bounds, operation IDs, event names and versioning. Error messages must distinguish forbidden, validation, conflict, retryable infrastructure and unknown outcome. Correlation IDs may aid support but never contain customer data.

Candidate outbox events: SaleFinalized, ReturnPosted, InventoryMovementPosted, PurchaseReceiptPosted, LoyaltyEarnRequested, CashSessionClosed, PayrollPosted and ReceiptDeliveryRequested. Define payload ownership and consumers once; names are proposals until T004.

T020 implements register cash control as an append-only ledger plus a mutable session projection. A nullable active guard under a unique register constraint makes the one-active-session rule a database invariant. Opening float is the first signed movement; expected cash is the sum of all signed movements. User-facing movement commands expose paid-in, paid-out, supplier-payment and no-sale-open only. Sale, refund, payroll, expense and correction kinds are reserved for their owning modules and must use a globally unique source key. A supplier cash payment must match the linked payment amount exactly, so financial evidence and drawer effect are one event viewed through two ledgers.

Closing stores an immutable physical-count record, server cutoff and movement high-water mark before revealing expected cash. Any pending server/offline sale keeps the session in `close_pending_sync` with expected cash concealed. Zero variance closes at launch; non-zero variance requires an owner/manager review reason. A late server cash movement after count recomputes expected cash, advances the version and returns the session to variance review. Reopening preserves count/review history but clears the projection's prior count comparison before further operation.

T035 owns fiscal mapping. Existing cloud-to-till transport IDs and `is_till`/`is_web` flags are not target-domain identity. Existing external connectors are reference material only.

## Configurations and defaults to freeze

- Shared/independent mode: immutable after onboarding configuration.
- Discount mode: merchant default with store override; future carts use the new published version. Existing carts must explicitly reprice or continue under a recorded allowed snapshot policy; T012 selects and tests it.
- Return window: proposed default 7 days; normal setting max 30; manager exceptions audited.
- Negative stock: warning and audit for permitted sales; expired batches blocked.
- Member portal: phone-only limited response, masked identity; no authentication claim.
- Light/dark theme: display preference only, never a tenant-wide pricing/config toggle.
- Fiscal applicability, tax rates, withholding and payroll statutory figures: never invent legal defaults.

## Performance and operations

Bound list queries, eager load intentionally, index by tenant/store and common predicates, and avoid loading entire sales history into checkout. Define a measured workload profile before assigning final latency targets. Use projected reports where useful with a clear freshness time and reconciliation to ledgers.

Protect backups, test restoration and account for tenant-scoped recovery. Deploy schema changes compatible with pending offline clients and workers. Version bootstrap/catalog payloads; do not release a client that cannot submit an older accepted pending-sale format without a migration path.

### Implemented offline PWA and reconciliation boundary (T023)

An active enrolled device obtains a schema-v1 bootstrap through `POST /api/v1/offline/bootstrap` using its one-time-issued device key. The server stores the exact device/store/register-scoped payload and returns its SHA-256 hash plus an HMAC-signed envelope. The shorter of the device lease and 72 hours bounds register/catalog/pricing use; cached staff authority is bounded to 24 hours. The payload contains only active assigned staff, sellable locations, authorized catalogue records, current published prices, unlimited promotions and explicit offline policy. Limited-redemption coupons are omitted.

The browser database `mypos-offline-v1` separates metadata, lease, catalogue, pricing, register session, sales, outbox, sync receipts and diagnostics. A strict read-write IndexedDB transaction stores the local sale/printable receipt and outbox command before success appears. Storage abort or quota failure leaves the sale incomplete. Pending and conflicted evidence is retained and exportable. The service worker caches navigation shell and versioned static assets, never API responses.

Web Locks grants one tab register-write ownership and `BroadcastChannel` announces ownership; a second tab remains read-only. Every command carries its original UUID, canonical payload hash, snapshot version, local commit time and fencing epoch. Connectivity uses a server health request rather than `navigator.onLine`. Reconnect posts bounded batches of 100 commands and retries the original identity.

The server first records the command ledger identity, then routes a cash sale through the existing cart, quote and `FinalizeSale` services. It rechecks the device fence, snapshot integrity/window, staff status/store assignment, pricing version, cash session, product/batch rules and authoritative total. Accepted commands link to the resulting aggregate; an exact retry returns it without reposting. Altered identity, stale pricing/fence/lease, expired batch and authorization failures remain explicit conflicts. Infrastructure failure keeps the command pending. Offline sale source is retained on the sale, and a late drawer movement drives an already-counted session back to variance review through the normal cash ledger.

T024 renders thermal commands and PDFs only from the immutable receipt snapshot. A print job is register scoped, idempotent, short lived and signed with Ed25519 by the server; the browser receives only the public key and signature. Offline bootstrap includes a signed device/register/fence capability expiring with the lease, so the helper can accept an offline receipt without a live cloud signer. Original, explicit reprint, helper attempt and drawer command identities are separate. Helper acceptance, reported paper output, failure and unknown outcome never alter sale finality. A sale-linked cash drawer command accompanies only an original cash receipt; other opens require server authorization, an active cash session, permission and a reason.

T025 uses a one-time, ten-minute pairing code to issue a distinct 16-hour read-only customer-display token. Only one pending/active pairing can exist per register, and issuing another revokes and clears the previous session. Staff publish a cart or sale identity; Laravel derives the customer-safe projection from the authoritative quote/sale instead of accepting arbitrary display content. The same-device offline path uses a random fragment-only channel ID, scoped register ID, monotonic sequence, `BroadcastChannel` and a minimal local snapshot. It provides no networked kiosk claim. Suspended/cancelled/disabled states clear basket lines; completed state clears after 30 seconds. The display has its own theme key and no write endpoint.
